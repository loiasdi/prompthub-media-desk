# MediaDesk 本地投稿实施方案：复用 AiToEarn 的 B 站适配代码

> 方案日期：2026-11-18。已落地 P1 的协议适配器和本地文件流，并有离线测试；还未接入 Host 路由、存储或发布按钮，尚未验证真实账号投稿。B 站为首个联调候选；第二个平台 [YouTube](local-youtube-publishing-plan.md) 独立实现，不是 B 站的依赖。

## 1. 要做什么

从 AiToEarn 开源后端抽取向 B 站投稿的代码，改造成 **MediaDesk 内的本地发布模块**。保留现有稿件、素材、发布页和 DSH 运行方式。用户选择已经归档的成片和封面、确认 B 站账号与投稿参数，MediaDesk 在自己运行的 DSH Host 上发起投稿，记录审核状态和作品链接。

```text
MediaDesk 发布页 → DSH Host（读取本地已选素材） → B 站官方上传及投稿接口
MediaDesk 发布页 ← 本地发布记录 ← DSH Host 查询 B 站稿件状态
```

- **不需要** AiToEarn 云端账号、API Key、MCP、Relay、自部署服务或 Chrome 扩展。素材不经 AiToEarn，不生成公网素材链接。若将 DSH Web 部署在远程主机，「本地」指该 Host 的文件系统及网络出口，不是访问网页的那台电脑。
- **首版**：B 站、单账号、单个选定成片、可选封面、立即投稿、状态查询与手动核对。平台确认封面或其他字段必填时由校验和界面据实要求。
- **不在首版做**：无人值守定时发布、多账号批量投稿、视频转码、修改或撤回远端作品、小红书和视频号自动发布。现有手动发布与日历排期不变，不会自动变成投稿任务。
- **不承诺规避风控**：本方案控制的是素材流向和调用方，不改变 B 站对应用权限、上传配额、内容审核等要求；不使用非官方创作中心接口、浏览器 Cookie 或登录态模拟作为兜底。

## 2. 上游证据与复用边界

上游基线固定为 AiToEarn [`11dd1957`](https://github.com/yikart/AiToEarn/tree/11dd1957d0c69ae2b27a0b8a47acdf6675715558)。参考目录是 `project/aitoearn-backend/apps/aitoearn-server/src/core/channels/platforms/bilibili/`。

| 上游文件 | 复用内容 | MediaDesk 适配 |
| --- | --- | --- |
| `bilibili.service.ts` | OAuth 授权地址、换取和刷新令牌、签名、分区查询；初始化上传、分片上传、完成上传、上传封面、提交稿件、查询详情 | 保留协议逻辑和经过验证的请求顺序。剥离 NestJS 注入与通用 HTTP/媒体服务；替换 URL 下载输入，改从已验证的本地文件流读取。使用 Host 端 HTTP 客户端。 |
| `bilibili-auth.provider.ts` | 授权和账号资料流程的参考 | 重写为 DSH 内的账号绑定流程。令牌密钥不进入前端或稿件文件。 |
| `bilibili-publish.provider.ts`、`bilibili-publish-options.provider.ts`、接口与异常定义 | 投稿选项、远端回执、审核与作品链接判定、平台错误映射 | 只保留首版需要的分区、稿件类型、文案、话题、封面和结果映射。提交回执 ID 不一律当作可公开访问的作品 ID。 |
| `bilibili.service.spec.ts`、`bilibili-publish.provider.spec.ts` 等 | 请求签名、上传和审核的已有测试思路 | 改为 MediaDesk 的 `node --test` 测试；默认 mock，不依赖在线账号或平台服务。 |

上游 B 站实现先申请上传、再从 `MediaService.withUploadSource()` 取可读范围的数据源并逐段送到 B 站上传地址，完成上传后提交稿件。**决定性改动是替换输入，不是重写 B 站协议**。上游分片大小、签名字段、封面上传方式和审核映射都是待验证的实现基线；以获权应用的当前官方文档和实际响应为准，不把上游常量当作平台保证。

不搬 AiToEarn 的 DSH 安装包、技能、浏览器扩展、NestJS 应用、MongoDB、Redis/BullMQ 或对象存储。小红书和微信视频号的上游后端主要登记浏览器端的发布结果，不能按 B 站的方式抽出一个本地官方投稿适配器。

**许可证交付**：AiToEarn 根目录许可证及上游后端包标注 MIT。移植前核对目标文件自身及父目录有没有不同声明；直接复制或改写受许可的部分时，保留 `Copyright (c) 2025 AiToEarn` 和完整 MIT 文本，记录提交、文件范围和改动。在打包白名单内放置上游许可，例如 `src/publish/bilibili/UPSTREAM-LICENSE.txt`，并检查 `.tgz` 确实包含。不要把单独标注 `Proprietary` 的 AiToEarn DSH 插件并入分发包。

## 3. 开工门槛：先验证应用权限

这里是最重要的前置环节。**能登录 B 站账号、能在创作中心投稿，不代表自己的开发者应用有 API 投稿权限。**

1. 在[哔哩哔哩开放平台](https://openhome.bilibili.com/)核对开发者资质、应用类型、稿件投递权限、允许的 OAuth 回调形式、可用账号及媒体限制。确认自己的应用能调用「上传 → 提交 → 查询」全链路，而不只是读账号数据。
2. 验证本机/自管回调：优先用已获平台批准的回调。如果平台允许 loopback，验证固定回调地址与 DSH 实际端口；如果只允许指定 HTTPS 地址，先确认现有自管 HTTPS DSH Web 是否能满足。未经批准，不把本机素材服务暴露到公网，也不引入 AiToEarn Relay。没有可用回调则暂停 OAuth 联调。
3. 用授权测试账号和明确允许投稿的短片，在隔离测试环境跑一次最小官方请求链路：换取令牌、验证账号身份、读取分区、上传并提交、取得可查询的回执及审核最终状态。真实投稿需人工确认；不带真实凭据跑 CI。
4. **继续条件**：证实应用能提交、能查询实际稿件，且 DSH 部署形态能安全持有凭据。任何一项不成立，保留手动发布，不先把自动投稿按钮开放，也不换 AiToEarn 的应用凭据顶上。

分发边界：先支持 **用户自备** B 站应用凭据。不能将共用 `clientSecret` 嵌入 npm 包、`dist/client.js` 或公共仓库。若未来希望普通安装用户无需自行申请应用，那是另一个产品方案，需要重新确认平台支持的授权客户端方式和密钥架构。

### 4.0 适配器边界（已实现）

- 调用方只通过 `createBilibiliAdapter()` 使用账号、分区、授权、`submit()` 和 `review()`；不从业务层直接调用协议客户端。稿件 ID、工作区修订号、账号归属、SQLite 和 UI 不下沉到平台适配器。
- `local-source.js` 是公共能力。它从 Host 私有暂存目录提供 `{ filename, mime, sizeBytes, stream({ start, end }) }`，适配器只消费可按范围读取的数据源，不接收路径或媒体 URL。此模块不负责创建不可变快照；只能在快照已固定后使用。
- 视频分片以 `application/octet-stream` 直传。`submit()` 要求调用方传入 `beforeSubmit`，由后续服务层在最终提交前持久化检查点。上传与提交不自动重试。最终提交响应只有明确的权限拒绝才归为 `failed`；服务异常、未知业务码、超时或回执异常归为 `unknown`，应先去 B 站创作中心核对。适配器不直接修改原稿状态。
- `errors.js` 定义公共 `PublishError`，带 `code`、`stage` 和 `outcome`；不带原始平台响应、请求 URL 或凭据。协议相关的字段名与错误码解析只留在 B 站模块。新增平台时先复用数据源与错误契约，避免现在先造通用任务引擎。

### 4.1 本地文件与发布快照

- 客户端只传 `itemId`、当前工作区 `revision`、账号 ID 和平台专属参数。后端从已保存的工作区读取标题、描述、话题、选定成片与封面；有未保存的编辑先保存。前端不传本机路径或任意 URL。修订号不符返回 `409`，要求重新检查并确认。
- 校验内容和素材归属、不是示例或回收站内容、媒体类型、文件存在性及平台当前限制。用 `realpath` 和受控文件打开方式拒绝逃逸、软链接和不符合范围的文件。外链和浏览器临时 URL 不能作为发布输入。
- 确认后在本地生成不可变的发布快照：实际发送文案、账号标识、分区和声明、文件大小与 SHA-256、受控副本 ID。首版采用**私有工作目录中的本地暂存副本**，可用写时复制时优先使用；否则流式复制。复制与校验完才开始上传，并在落盘前复查修订号。后续改稿、换封面、回收原素材都不会替换已确认待发内容。
- 大视频上传使用 `fs.createReadStream` 按区间读取，不整段进内存。不把 `Store` 的全局文件锁持有到网络上传结束。现有素材导入上限为 250,000,000 字节，首版不暗中放宽，高于上限的真实用例单独验证容量与导入策略。
- 暂存文件不放在 Obsidian 同步目录或普通静态文件路由；使用 Host 私有目录，按任务和工作区隔离。任务终结后按明确保留期清理暂存但保留发布记录；远端结果待核对时保留对应回执和指纹，不静默丢弃。首版有进行中或待核对任务时阻止迁移存储目录并提示先处理；工作区作用域的记录需纳入迁移测试，凭据不随内容导出。

### 4.2 OAuth 与权限

- 账号授权由已登录的 DSH 用户主动发起。生成不可预测、短时、一次性且绑定发起会话/工作区的 `state`；回调严格匹配应用配置、校验 `state` 并防重放。是否使用 PKCE 取决于获权应用的官方支持，不擅自假定。
- 不放宽 `/media-desk` 的统一鉴权。若官方回调跳转无法携带 DSH 凭据，只能设计一个隔离的最小回调：验证并消费绑定的 `state`，完成换码或交给已登录会话继续，不开放读取或发布能力。不在回调页面透露授权码、令牌或文件信息。
- `clientSecret`、`accessToken`、`refreshToken` 只在 Host 侧使用；优先使用经宿主验证可用的系统凭据存储。若首版采用独立本地凭据文件，只能位于 Host 私有目录，POSIX 目录 `0700`、文件 `0600`，其他平台验证等价权限；不能依赖 Obsidian 同步目录或普通设置接口。账号断开清理本地令牌；远端撤销能力以官方支持为准。
- 前端只读账号昵称、平台 UID 或本地账号 ID、连接状态。投稿时再次核对选中的账号与凭据关系；刷新令牌时同账号串行，日志与错误响应脱敏。只访问适配器固定的官方地址，不接受用户传入的投稿 URL，也不跟随跨域重定向发送凭据。

### 4.3 状态、重复投稿与恢复

沿用[总体方案](content-video-assets-publishing-plan.md)的独立 `publish.sqlite` 存储方向；不迁移现有 `state.json`。先验证 SQLite 驱动在本项目支持的 Node/DSH Desktop 和 Web 打包中可安装；未验证前可先写适配器和 mock 测试，**不以仅进程内变量临时替代生产去重**。首版不需要通用调度队列。

| 状态 | 含义与允许操作 |
| --- | --- |
| `prepared` / `uploading` | 快照已固定或上传中。DB 原子领取同一任务；同一确认动作重复提交返回已有任务。 |
| `submitting` | 已持久化进入最终投稿边界，再调用 B 站提交。若这一步响应丢失，不自动重发。 |
| `pending_review` | B 站已接受并返回可查询回执，但作品还未确认公开。可刷新/后台有限轮询，不标已发布。 |
| `published` | B 站给出明确成功状态，并取得可验证的最终作品标识；有可靠 permalink 时显示作品链接。 |
| `failed` / `rejected` | 前者为明确的本地或接口失败，后者为 B 站明确拒绝或审核未过。记录原因；用户重新确认后才开始新尝试。 |
| `unknown` | 提交可能成功但无法确认，或长时间无法核对结果。显示「去 B 站创作中心核对」；有回执就查询，无回执时不猜测匹配、不自动重投。 |

任务表保存快照 ID、账号本地 ID、当前阶段、尝试 ID、远端投稿回执、最终作品 ID、可用链接、审核状态、错误摘要及时间。用事务和唯一键抵御双击、两个 Host 和重复请求；通过持久化检查点判断恢复方式。**本地可做到同一次确认只领取一次，但没有经验证的远端幂等保证，就不能宣称跨网络恰好一次。** 仅对只读查询做有界退避重试；上传步骤仅在官方语义证明可安全重试时做分片级重试。无确定证据，不重试最终提交。

DSH 重启后按已保存回执恢复状态查询；最终提交前中断的任务按明确检查点恢复或要求重新确认，不因重启自动发出新稿件。已提交的稿件审核在 B 站继续进行。界面以发布记录为准，普通撤销、改稿或清空样例不能撤销远端投稿或擦掉既有发布结果。

### 4.4 接口草案

以下均为拟新增的 MediaDesk 接口，不是上游现成接口；使用 `/media-desk/` 前缀。OAuth 回调若需专门入口，以第 3 节验证结果为准。

| 接口 | 用途 |
| --- | --- |
| `GET publish/bilibili/accounts`、`POST publish/bilibili/auth/start` | 查询脱敏账号、开始授权；断开授权另走显式操作。 |
| `GET publish/bilibili/categories?accountId=…` | 读取有效投稿分区，短时缓存在 Host。 |
| `POST publish/check` | 校验指定工作区、选材和投稿参数；仅检查，不提交。 |
| `POST publish/start` | 接收确认请求 ID、稿件 ID、修订号、账号和投稿选项；创建或返回同一确认动作的任务。服务端重新校验，不以此前的检查替代。 |
| `GET publish/tasks?itemId=…`、`POST publish/tasks/:id/refresh` | 查询状态或明确请求查远端；不可通过查询创建投稿。 |
| `POST publish/tasks/:id/reconcile` | 人工登记核对结果，区分「手工补录」与「远端已验证」，不凭未验证链接自动变成远端成功。 |

## 5. 施工顺序与验收

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| P0 权限与协议验证 | 获权应用、回调验证、素材限制、真实最小投稿结果 | 自有应用能走通授权、上传、提交、查询。未通过时不开放自动发布。 |
| P1 提取 B 站适配器 | 独立适配器、输入替换、许可与上游映射、HTTP mock | 本地文件可按字节正确上传；请求只到官方目标；签名、令牌刷新、分区、封面和稿件回执有可重复测试。 |
| P2 连接 MediaDesk | DSH 账号配置、快照、记录与恢复、发布页和手动回退 | 用户确认后才执行；修改稿件/素材不影响快照；重复点击仅创建一个任务；超时后不重投；结果重启后可查。 |
| P3 真机验收与发布 | 在受支持的 Desktop/本地 Web 验证、完整回归、安装包检查 | 用选定的本地成片成功投稿并在审核后回写作品；网络证据显示不访问 AiToEarn、不把素材传入其他存储；手动发布路径不受影响。 |

**必测异常**：缺权限或过期令牌、授权失败或回调重放、工作区修订冲突、使用其他稿件素材或访问越界、文件缺失/换档、分片边界与上传受限、中途断线、最终提交后超时、远端回执无公开作品 ID、审核不通过、双 Host 竞争、Host 重启、工作区换目录、凭据没有进入序列化响应或日志。真实发布试验只检查官方应用和测试账号，不用来获得风控结论。

**常规验证**：运行 `npm ci`、`npm test`、`npm run build`、`npm pack --dry-run --ignore-scripts`；在 DSH Desktop 和 Web 实际安装验证驱动及凭据访问。检查包内许可、运行时模块和产物，不包含开发者密钥或真实素材。首发按能力开关启用 B 站自动投稿；关闭后禁止新提交，历史记录和必要核对仍可用，旧版本的手动发布可继续使用。

## 6. 做完之后

第二个平台 [YouTube](local-youtube-publishing-plan.md) 已实现同结构的协议适配器。平台独立验收：必须用自己的应用授权并验证本地流式上传和回查，才开放相应发布入口。快手等其他平台另行评估；抖音的手机确认应单独设计为「待用户操作」，小红书、视频号继续手动发布。若未来要求关掉 DSH 也能到点投稿，必须另立方案，优先验证平台原生预约能力；本文不引入常驻服务。
